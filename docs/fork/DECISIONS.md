# Implementation decisions

Decisions made while building Meditejo, newest last. Product decisions live in `BRIEF.md`; this file holds the implementation calls made on the way, with the reason for each, so they can be revisited deliberately. Mark a decision **provisional** when it waits on Burooj.

## 2026-10-15

- **Flutter 3.47.2 / Dart 3.13.2**, matching `flutter-version` in `.github/workflows`. On bjslab it is installed under the user at `~/.local/share/flutter`, with `flutter` and `dart` symlinked into `~/.local/bin`.
- **The Dart package keeps the name `medito`.** Renaming it would rewrite every `package:medito/` import, conflict with all concurrent work, and make cherry-picking from upstream expensive. Users see the display name, application ID and icons, which do change.
- **Application ID `io.github.beejsbj.meditejo`.** It is settled, installed on the S23+ on 2026-10-15. It is a reverse domain Burooj controls through GitHub, and F-Droid accepts it. Pick it before the first phone install, because changing it later means installing a separate app.
- **One durable signing key, kept on bjslab.** Every APK installed on the phone is signed with the same Meditejo key, because a key change forces an uninstall, which deletes the local-only stats and favourites. The key never goes to Daytona: the cloud builds the APK and bjslab signs it with `apksigner`. Burooj approved a backup (2026-10-16). The key is in BWS infrastructure as `MEDITEJO_SIGNING_P12_B64` and `MEDITEJO_SIGNING_PASSWORD`, and the round-trip was verified.
- **Build route (superseded by GitHub Actions, below):** resolve dependencies on bjslab, where pub.dev is reachable, and ship the pub cache with the Daytona upload (`--profile android`), where pub.dev is blocked. Gradle and the Flutter engine artifacts download inside the sandbox. Details are in `BUILD.md` once the route is proven.
- **Medito mock mode is the baseline, built but not installed.** The phone's remote-control MCP has no uninstall tool, so only Meditejo-named builds with the durable key go onto the phone.
- **Placeholder icon** until Burooj chooses a mark. This is a design decision to make later, not part of the build.

- **Rename identity:** Android defaults to `io.github.beejsbj.meditejo` without `keystore.properties`; an explicit `appId` still overrides it. Missing signing properties leave release output unsigned for the build worker's durable-key signing route. The Kotlin namespace and generated Pigeon package remain `meditofoundation.medito`; manifest component names are explicit so the namespace is independent of the installed ID. File-provider/startup authorities already derive from `${applicationId}`. Native audio intent actions use the new identity.
- **One phone identity across flavors:** `dev` and `prod` both install as `io.github.beejsbj.meditejo`, labelled **Meditejo**. `dev` keeps the `-dev` version suffix, with no application-ID suffix. This makes the everyday build a stable install; flavors cannot coexist. Use the same durable signing key for phone updates, as already required above.
- **Deep links:** the fork owns the `meditejo` custom scheme (Android widget links use `meditejo://meditejo/...`; iOS also accepts `meditejo://tracks/...`). It does not register upstream's `medito.app` HTTPS links. Dart parsing and native widget URLs change together. iOS config uses the same base bundle identifier, `.widget` for its extension and `group.io.github.beejsbj.meditejo.widget` for shared storage. Native class/target names and internal method channels remain unchanged.
- **One placeholder mark:** an original cream circle on muted sage, authored in `assets/branding/placeholder.svg`. Run `uv run scripts/regenerate_icons.py` to update Flutter, Android and iOS resources. Removed upstream alternate artwork, launcher aliases, the icon-selection sheet and `dynamic_app_icon_flutter_plus`; settings shows a static preview. The generated Pigeon icon API remains as a no-op for the primary icon, avoiding unrelated API/codegen churn. A real mark and variants can be added later.
- **Credit and language:** settings → Advanced → About Meditejo credits Medito by the Medito Foundation, AGPL-3.0, with links to upstream and fork source. English, German and Spanish app-name strings and generated localisations change; Foundation/content/donation/commerce strings stay for the parallel service-removal worker. The README describes this independent fork without store/download links; LICENSE is unchanged.

- **The app now uses local repositories without a mock switch.** This supersedes the earlier mock-mode build baseline. Removed `lib/mock` and `MOCK_MODE`, including its proprietary sample catalogue. `LocalCatalogue` is deliberately empty and injectable; no request falls back to Medito. Unknown saved source IDs are unavailable locally. Future source adapters use the existing repository model contracts; see `ARCHITECTURE.md`.
- **Launch directly into the local home.** Startup has no account, service-health, payment or analytics initialization barrier. Local reminder preferences remain in settings; the local onboarding screens remain available for their existing preferences/debug flow.
- **Stats and favourites are device-owned.** Kept local session storage, completion flags, streak/consistency calculations, manual sessions, native completion replay, reminders, home widgets and optional Health writes. Removed server sync, backup and account conversion prompts. This slice adds no replacement export/backup system.
- **No bundled ambient catalogue yet.** The included bell is a session cue rather than a soundscape. Timer bells remain bundled and work through the shared player; ambient lists start empty pending licensed sources. Existing preferences are retained without exposing old server catalogue URLs.
- **Firebase functions were service infrastructure.** Inspected `firebase/` before removal: its Cloud Functions served the Medito integration rather than local app functionality. Firebase core, analytics, crash reports and remote messaging are removed; local notifications remain.
- **Provisional: retain the standalone local feedback/rating component.** Store-rating policy is outside the named removal list, so the reusable widget, previews and tests remain; the personal end screen no longer reaches it. Its inherited store-listing target should be reviewed before any future reuse.
- **Branding links remain the rename slice's responsibility.** This branch retains inbound `medito.app` link matching, pack/track share URLs, share-copy branding and native channel/application identifiers. None is a content API, account, stats or tracking request. The rename worker must reconcile these overlapping files when integrating.
- **Calendar-day stats use calendar arithmetic across DST.** The original stats suite reproduced ten failures on bjslab. Fixtures now construct their intended local dates instead of mixing UTC timestamps or subtracting elapsed 24-hour periods; consistency iteration likewise counts calendar dates, matching the native calculation. Expected scores are unchanged.
- **Preserve existing on-device downloads and metadata.** Empty catalogue lookup can resolve a saved download by ID, so favourites can reopen it. This does not reintroduce a remote metadata lookup or ship a Medito catalogue. Existing user metadata may retain its original source/artwork URLs; this slice does not erase user data.
- **Local completion acknowledgement is durable.** With server recovery removed, completion and repeat IDs are saved in the same local stats record as their counters. Concurrent callbacks join the pending save, rejected writes reload storage before retrying, native callbacks acknowledge only true, and queue drains retain new enqueues. Receipts survive deleting a session so delayed replay cannot resurrect it; the additive field defaults empty for older histories.

- **Integrate as a merge stack: #3, then #2.** The rename branch merges `fork/remove-medito-backend` without rewriting history. Deleted service/mock/sign-in files stay deleted; local startup, navigation and surviving settings come from that branch. Localisation uses its reduced key set plus four About/credit keys, with generated Dart output rebuilt. Both earlier decision sets are retained above in chronological order.
- **Share the fork identity after service removal.** Stats sharing links to the fork source; quote cards identify Meditejo; track/pack links, widget/Siri routes and the local-timer Maestro flow use `meditejo:`. Upstream Foundation links remain only for credits/provenance, never as this app's landing page. This completes the earlier branding-links handoff.
- **iOS lockfile is deferred to macOS.** With no CocoaPods tooling on bjslab, integration keeps de-Medito's `ios/Podfile.lock` exactly as requested. It still records the obsolete alternate-icon plugin; `pubspec.yaml` and both regenerated Dart lockfiles remove that plugin. Run `pod install` before an iOS build to reconcile the native lock. No iOS runtime or signing claim is made here.

- **Daytona was tried and retired (build worker).** The pub cache was shipped in the upload, and the plugin-portal artifacts were staged over HTTPS (the portal resets TLS from Daytona). Blocked JitPack and JCenter hosts were dropped in the sandbox. Even a lean arm64 debug build overflowed the account's 10 GiB sandbox cap: Gradle home 5.3, Android SDK with the required NDK 2.8, and Flutter 1.1 GiB. The NDK is needed because `path_provider_android` uses `jni`, which compiles C. The evidence is in `BUILD.md` under "Routes tried".
- **GitHub Actions unsigned APK, bjslab signing (supersedes Daytona and the mock baseline):** Burooj chose GitHub's public-repository hosted runner after the 10 GiB Daytona cap blocked the lean arm64 build. `meditejo-apk.yml` builds the renamed/de-Medito stack using Flutter 3.47.2 and the runner's normal Android SDK/NDK, with no private build inputs. Release signing is conditional on a supplied store file; the minimal Gradle change matches PR #2, so no throwaway release key is needed. Debug signatures are removed before artifact upload too. Only unsigned APKs/provenance are retained for seven days, with no published release. The existing durable key stays on bjslab; the local script pins its public SHA-256 before and after signing. Pushes to `apk/**` bootstrap the route before the workflow reaches the default branch; temporary build refs carry the exact commit and build parameters. The phone candidate integrates PR #2 head `b7c3f8ec` (including PR #3) with this route on `apk/m1-phone`.
- **Let the APK command regenerate release plugin registration:** the first GitHub compile reached Java and failed because `--no-pub` preserves the initial debug registrant (including integration_test), whereas Gradle excludes dev-only plugins in release. Remove that optimization and use the normal `flutter build apk` command. Flutter 3.47.2 source confirms that `--no-pub` skips platform tooling regeneration; no app/dependency change is needed.
- **Use the existing PKCS12 password once with apksigner:** `--ks-pass file:...` is sufficient because the private key uses the same password. Passing the same single-line file again as `--key-pass` consumes a nonexistent second line. The successful local signing command omits that argument and closes stdin; the durable key/password are unchanged.

## 2026-10-16

- **Health sync is opt-in from Settings.** The Health Connect / Apple Health row is now a saved switch. Only switching it on requests permission; denial leaves it off with a short explanation. Player initialization and completion never request permission. Granted, enabled sessions retain the existing write and deduplication flow; unavailable permissions and failed writes are logged without UI or retries that request access.
- **Migrate from the current OS grant once.** Missing `healthSyncEnabled` is initialized by a silent permission check: a current grant keeps sync on, otherwise it starts off. The old `healthAuthRequested` flag only records a prompt, so it is not consent. An explicit off persists even if OS permission remains granted. Both Android and iOS use this policy. HealthKit checks WRITE permission silently because its READ_WRITE check always returns an undetermined result; the Settings request retains the existing READ_WRITE scope and checks the write grant afterward. No iOS runtime verification was performed.

## 2026-10-17

Dharma Seed data layer and the source seam (PR A of slice 2).

- **One small source interface, routed by ID prefix.** `ContentSource` (seven methods: prefix, browse, pack, track, pack track IDs, pack search, track search) is the whole contract a source implements. `ContentRouter` dispatches by prefix and falls back to `LocalCatalogue`, and the existing repositories delegate to it, so PackView, the player, downloads, favourites and completion did not change. Search is part of the interface because every planned source (RSS, YouTube imports) also searches local metadata.
- **drift on a bundled SQLite, with FTS5.** Android's framework SQLite does not reliably ship FTS5, so the app bundles its own through `drift_flutter`/`sqlite3_flutter_libs`. drift also gives typed queries and an in-memory database for tests. Host tests load the system `libsqlite3` (falling back to `libsqlite3.so.0`, the only name on bjslab), through a `sqlite3` dev dependency. The generated `dharma_seed_database.g.dart` stays untracked like every other `.g.dart`; CI's build_runner step produces it. The database opens lazily, so constructing it touches no platform channel at startup or in unrelated tests.
- **IDs carry the record kind:** `ds-talk-<id>`, `ds-retreat-<id>`, `ds-teacher-<id>`. Dharma Seed's talk, retreat and teacher numbers overlap, and these IDs are stored permanently in stats, favourites and downloads.
- **Sync order: teachers, then retreats, then talks.** Teachers and retreats take about a dozen requests and are enough to browse courses; the ~49k talks follow in the background. Opening a course or talk that hasn't synced fetches it, and its teachers, ahead of the background queue on the same serial lane, so priority never means parallel requests.
- **Politeness numbers:** one request at a time with at least 750 ms between requests; detail batches of 250 teachers, 250 retreats and 500 talks (a 500-talk batch is about 360 KB and 2.7 s live); a 45 s timeout; up to 4 attempts with 2/4/8 s backoff on 429, 5xx and network errors, and no retry on other 4xx; incremental by edition after the first run; automatic syncs 3 s after launch, at most every 12 h; manual refresh any time. User-Agent: `Meditejo (personal meditation app; +https://github.com/beejsbj/meditejo)`.
- **Resumable by construction.** Listed IDs go into a database queue together with a pending edition. A batch is upserted and dequeued in one transaction, and the edition is recorded only when the queue is empty. A killed app resumes the queue, and a resumed run skips kinds that finished within the auto-sync interval.
- **Removals.** `x_items` from an ID listing are deleted. A requested ID that a detail response omits is gone upstream: it is dequeued and pruned from its retreat's talk list, so it is neither refetched forever nor counted against course progress. Talks with `retreat_id` 0 are stored without a retreat. The background sync never requests a talk the listing omits, so once every talk has synced, a retreat's listed ID with no stored talk is treated as gone when counting completion and when opening the course (`liveTalkIdsOf`); until then the retreat's own list stands.
- **No teacher contact data.** Teacher records include addresses, and for some teachers personal emails (`address1`/`address2`). Only name, bio, photo, website and flags are stored. Fixtures blank those fields too.
- **Completion ticks only for saved or started courses.** `PacksRepository.fetchPackTrackIds` gained `startedTrackIds`; `packTrackIdsProvider` now watches stats and passes `tracksChecked`. The Dharma Seed source answers with saved retreats plus retreats containing a completed talk, using each retreat's own talk-ID list, which is complete before its talks sync. The bundled catalogue ignores the parameter.
- **Temporary browse and search wiring (until PR B).** Explore lists saved retreats, then the 40 most recent (by `start_date`), refreshing when a sync pass changes records. Search merges source FTS results for courses into the existing pack filter; talks already went through `searchTracks`. Home is unchanged.
- **Kind from `recording_type`:** `Meditation` → guided meditation, `Chanting` → chanting (both **Practice**); `Talk`, `Q & A` and anything else (`Other`) → **Talks**. Live counts on 2026-10-17: Talk 38,776; Meditation 6,253; empty 2,956; Other 531; Q & A 339; Chanting 139; Jataka 1 (empty and unknown read as Other). **Provisional:** chanting counts as Practice because it is done along with the audio. Practice kinds allow background sound; talks don't. `Track` gained no field: the kind label leads the subtitle ("Guided meditation · Rob Burbea · 42 min"), and PR B can read `DharmaSeedKind` from the database for chips.
- **Attribution hook now, attribution UI in PR B.** The player already links the artist line, so a talk's artist is its teacher, linked to the talk's dharmaseed.org page. Audio is the original file at `https://dharmaseed.org<audio_url>`, unmodified; Dharma Seed redirects it to its media host. No Dharma Seed content is bundled.
- **The sync status row lives in Settings → Customization** as a provisional place, with progress, last sync or failure, and refresh on tap. Its strings are localised (en/de/es). Mapping subtitles ("talks", "Guided meditation") are English for now.
- **A live check, not a CI test.** `tools/meditejo/dharma_seed_live_sync.dart` runs one full and one incremental sync against the real API and prints timings. Run it by hand only.
- **Measured against the live API (bjslab, 2026-10-17).** A fresh sync had teachers and retreats stored after **38 s and 25 requests**. The full catalogue (1,235 teachers, 4,361 retreats, 48,995 talks) took **385 s and 124 requests**, transferring 37.5 MiB into a 48 MiB database. An incremental sync right after took 4 requests (3.3 s). FTS queries on the full index take 9–63 ms for specific terms, and 355 ms for a broad one ("metta", about 3k matches, ranked by bm25). PR B's search should debounce, and may rank titles before descriptions if phones are slow. 636 teachers have no photo, and 179 retreats have no talks; browse skips the latter.

The Dharma Seed experience (PR B of slice 2): Explore, search, course and teacher pages. Everything below is **provisional** until Burooj has used it on the phone.

- **The seam stayed as PR A built it.** `ContentSource` has the same seven methods. Saving is an optional second interface, `SavableContentSource` (`canSave`, `isSaved`, `setSaved`), which `ContentRouter` asks only of the source that owns the ID, so a source that cannot save needs no stub. Teachers, the Practice/Talks groups and the session-length filter are Dharma Seed methods on `DharmaSeedSource` (`explore`, `search`, `teacherPage`, `teacherTalks`), not interface methods: with one source the shared shape is a guess, and RSS or YouTube will show it. What *is* general went into the shared models as optional fields, so any source can fill them and the screens read only models: `PackModel` gained `teacher` and `attribution`, `PackItemsModel` gained `kind`, `teacher`, `durationMs` and `date`, and `Track`/`PlaybackRequest` gained `attribution` (`SourceAttribution`: source, creator, page URL, licence name and URL).
- **Explore chips are toggles; none selected shows everything.** Practice is guided meditation plus chanting; Talks is talks, Q & A, other and untyped (the mapping PR A recorded). A **course** counts as Practice when at least half of its stored talks are practice, otherwise as Talks, so a mixed retreat appears under exactly one chip. Retreats whose talks have not synced yet cannot be classified and appear only without a chip. Singles ("Latest guided practice", "Latest talks", 20 rows) appear only once a chip is chosen, because without one Explore is about courses. Saved courses and teachers lead only the unfiltered view; filtering saved courses by group would hide the user's own choices behind a chip. Courses are the newest 40, teachers the 20 with most talks (co-teaching counts, so a teacher's strip number matches their page).
- **Generated art, one palette.** A course, teacher or session with no picture gets `GeneratedArtwork`: a diagonal two-tone gradient from eight muted pairs (sage, dusk, clay, lilac, sand, moss, lagoon, dust rose) with three faint rings, chosen by an FNV-1a hash of the title. FNV rather than `String.hashCode`, so a course keeps its colour across launches. 636 teachers have no photo, so this is the common case, not the edge. Portraits are cropped from the top, to keep faces. The player uses the same art, blurred, behind a talk with no cover.
- **Search is local and grouped.** Teachers, then Courses, then Talks (teachers lead because a talk quoting "Rob Burbea" outranks his own talks). The debounce is 400 ms (a broad query takes about 350 ms on bjslab). The old ASCII-only filter on the query is gone: the FTS index folds diacritics itself, and the filter would have deleted the letters of "Ñāṇavīra". The session-length filter (any, under 10, 10–20, 20–30, 30–45, over 45 minutes; buckets are `[min, max)`) narrows talks only, since teachers and courses have no length. The empty page offers four suggestions (Rob Burbea, metta, jhana, emptiness), taken from the brief's own material; they are English text in code, easy to change. The grouped search reads Dharma Seed only; the seam's `searchPacks`/`searchTracks` still serve other sources and will join it when the second one arrives.
- **The course page is PackView, extended.** A pack is treated as a *course* when it carries a teacher, an attribution or session kinds (`_isCourse`); anything else keeps the original layout, so nothing else changed. A course gets the progress line ("N of M left"), the next session named under it ("Resume: …"), Save course, and Sessions / Summary / Teacher tabs (a tab with nothing to show is dropped; a lone Sessions tab shows no bar). The one primary button is still the existing `PackPlayButton` (it docks under the app bar on scroll, which suits 60-talk retreats), and its label string changed from "Continue" to "Resume" to match Waking Up. The description moved from the header into the Summary tab for courses. **Day grouping:** a course of eight or more sessions, all dated, spanning two or more days is grouped under day headings; the heading reads "Day 3 · Sat, Mar 14" when the whole course fits in 21 days (a retreat) and only the date otherwise (a years-long series, where "Day 412" would mean nothing). A group whose sessions are all played shows a tick. Credit and licence close every tab.
- **Session rows** (`PackItemWidget`) show a kind label, the title, "teacher · N min", a downloaded mark (from the saved-downloads list) and the played tick. The same rows serve Explore, search and the teacher page; outside a course they show the tick but no toggle. Rows open the talk's page.
- **The teacher page is a new screen** (`TeacherView`), since PackView cannot express it: photo as the large app bar, counts, Save teacher, website, plain-text biography (Dharma Seed bios are plain text), their courses, and their talks newest first, 30 at a time with "Show more talks". A course's Teacher tab links to it.
- **Attribution, per the licence.** `AttributionNotice` shows "teacher · Dharma Seed" (a link to the talk or course page), "Licence: CC BY-NC-ND 4.0" (a link to the licence) and "Streamed as recorded, unmodified." It appears under the description in a talk's details, as a compact line under the title in the player (portrait and landscape), and at the foot of the course and teacher pages. The audio is still the original file; nothing is re-encoded or mixed by this slice. The player's artist link to the talk page stays.
- **Completion: unchanged, and now tested not to fire on open.** Medito's rule is that a session is complete when playback reaches its end (ExoPlayer `STATE_ENDED` natively, `completed` on iOS), with a 5 s guard against load artefacts (`SessionCompletionGate`). There is no percentage threshold to reuse. Only that path, the per-row toggle and "mark all" write `tracksChecked`; opening a course, a talk or the player button writes nothing, and a test pins it. **Open question for Burooj:** a 90-minute talk then counts only if heard to the very end. A "90% counts" rule is a native change (Kotlin and Swift) and would also count a talk whose closing silence he skips; say if he wants it.
- **Pull to refresh on Explore forces an incremental sync** (a few requests, not awaited) and re-reads the lists. While the first sync runs and no course has arrived, Explore shows a card with the live progress instead of an empty grid.
- **Sync decoding moved off the main isolate** for bodies over 32 KiB (`Isolate.run`); smaller ones decode inline, since an isolate costs more than they do.
- **Strings** for the new screens are in en, de and es. The kind labels in subtitles ("Guided meditation", "Talk") and the retreat subtitle ("38 talks") are still English from the data layer, as PR A left them.
- **No temporary Home section was added.** Explore shows saved and recent courses, which is enough to test with; Home waits for the "Continue your practice" slice.
- **Widget tests drive the real source over an in-memory database** (`test/helpers/dharma_seed_app.dart`), so a tap on a row really opens the next page, instead of mocking providers screen by screen.
- **Details settled after an independent review of the slice.** A download keeps its credit (`Track.attribution` is stored with the saved metadata, so the Downloads list and the player show it offline). A talk with no recorded length (stored as 0) is in no length bucket, so "Under 10 min" never lists it. Teachers marked non-public are left out of search as well as Explore. Day numbers count UTC dates, so a daylight-saving change inside a retreat cannot shift them. With a chip chosen and no talks synced yet, Explore shows the "setting up" card instead of "nothing here", because courses cannot be classified until their talks arrive. Search re-runs when a sync pass lands records. The teacher's course list holds up to 500 courses and the counts line uses plural forms. Teacher-strip height and the length-pill row follow the text scale, and pills and credit links are at least 44 dp tall. The hidden placeholder copy of the course play button no longer exposes semantics, so a screen reader hears one button.
- **Background sound under Practice recordings is a playback layer, not an edit.** The app mixes a chosen ambient sound as a separate stream next to the original audio file, which stays byte-for-byte as published, so "Streamed as recorded, unmodified" describes the file. Whether layering counts as a derivative under CC BY-NC-ND is a licence reading, not a code question; talks get no ambient layer by default and Practice recordings get it only if the user switches it on. Flagged for Burooj.

In-app updates from GitHub Releases (slice 12; BRIEF decision 12). Design in `docs/fork/UPDATES.md`. Everything is **provisional** until the first release has updated the phone.

- **Version codes are `YYMMDDnn`, chosen by the script, never by hand.** Medito's last build is `302473`, and Android refuses a lower code, so Meditejo needs a code that only ever rises. Build date plus a two-digit counter (`26101701`, `26101702`, then `26101801`) does that with no state beyond what already exists: `release.sh` takes the later of "today's first code" and "highest code so far + 1", where "so far" is the larger of `pubspec.yaml` and the latest published `meditejo-release.json`. It refuses a 100th release in one day and anything above `int` range (which is year 2147). Version *names* are plain `MAJOR.MINOR.PATCH`, set by hand; the updater only compares codes.
- **First version: `0.1.0`**, with `pubspec.yaml` at `0.1.0+26101701`. The test APK built from this branch is therefore the installed build, and the first published release (`0.1.0`, code `26101702` or later) is something to update to.
- **Releases use the `prod` flavor.** Both flavors install as `io.github.beejsbj.meditejo`, so each would update the other. `dev` appends `-dev` to the version name and has its own launcher icon; `prod` is the plain app, and its name is what the About page and the update line should show. The consequence is that the first `prod` release replaces the dev icon on the phone. `dev` stays the `build_apk.sh` default for test builds. The `prod` flavor has not been built on CI before; `build_apk.sh --flavor prod` exercises it.
- **The release carries its own `versionCode` in a small `meditejo-release.json` asset**, beside the APK, its `.sha256` file and the notes (the release body). A tag or asset-name convention would have to be parsed back out of a string; the manifest is explicit, versioned (`schema: 1`), and also holds the hash and size. The APK's URL still comes from the API's own asset list and must sit under this repository's release downloads, so a manifest cannot point the app at another host.
- **One API request a day.** The check sends `If-None-Match`; a `304` saves bandwidth but still counts against GitHub's 60-an-hour unauthenticated limit, which one request a day cannot reach. The launch check runs 10 s after startup (after the first Dharma Seed requests) and at most every 24 h; a last check in the future (clock set back) counts as due; failures on launch are silent and do not count as a check, so the next launch tries again. "Check for updates" always runs and is the only place errors are shown. The last release and its ETag are cached so the update line survives a restart without a request.
- **Two checks before Android sees the file.** Dart checks the SHA-256 against the published hash while saving (the file only gets its final name once it matches). Kotlin then reads the APK's signing certificate with `getPackageArchiveInfo(…, GET_SIGNING_CERTIFICATES)` and `UpdateSignaturePolicy.signersMatchPin` requires **exactly one** signer whose certificate digest is the pinned one; it also requires our package name and the announced `versionCode`. A mismatch deletes the file and says so calmly. Several signers are refused even if one matches. The pin lives in Kotlin and is the same digest `build_apk.sh` and `release.sh` check, so a key rotation would mean a new pin shipped in an update signed by the old key.
- **`PackageInstaller` sessions rather than `ACTION_VIEW`.** Sessions report the outcome (success, user cancelled, blocked, conflict), stream the APK from the app's private directory with no file URI, and are the supported route on Android 14 and 15. So no FileProvider paths were added. Every update shows Android's confirmation prompt: skipping it needs the `UPDATE_PACKAGES_WITHOUT_USER_ACTION` permission, which is not declared. If no result arrives within three minutes (the prompt could not open, or sat unanswered), the app returns to "update available". The callback is an explicit, mutable `PendingIntent` to a non-exported receiver, as Android 14 requires.
- **"Install unknown apps" is explained once.** Without it, the update stops before downloading, shows one calm paragraph with an "Open settings" button, and opens `ACTION_MANAGE_UNKNOWN_APP_SOURCES` for this package; when the app resumes with the switch on, the update continues by itself. Later updates open the settings page straight away. Whether the grant is on is checked, never assumed.
- **Closing Android's install prompt is not an error.** The About page returns to "Update available"; the verified APK stays for the retry, and a retry reuses it if its hash still matches. Leftovers (`.part` files and APKs not newer than the installed build, which includes the one that just installed) are deleted on the next launch.
- **Calm UI.** No modal anywhere. The update lives in About Meditejo (now a page, replacing the old About dialog, with version, build, credits and the update section). Home gets at most one dismissible line per version ("Meditejo 0.1.1 is available · View ✕"), which stays dismissed after a restart and speaks again only for a newer version. The dismissal does not hide the update on the About page. Errors are one plain sentence each: offline, rate-limited, unavailable, download unfinished, hash mismatch, signature mismatch, wrong file, install refused. ## 2026-10-17 (slice 3, PR C1: library-first import)

Product questions here were settled with a reasonable, reversible choice and are flagged for Burooj at the end.

**The library**

- **A separate database for the library**, not a table in the Dharma Seed one. The catalogue database is a replaceable copy of someone else's data and is about to be swapped for a bundled snapshot (PR C2); a library inside it would be lost or have to be migrated each time. `meditejo_library.sqlite` holds only the user's own entries, positions and imports, so it survives any catalogue change.
- **One entry shape for everything kept.** `source_id` (any `ds-…` or `lib-…` ID), `kind` (course, single or teacher), the detected and the overridden Practice/Talks group, a title and a title override, and a snapshot of subtitle, artwork, count and length so the library draws instantly and offline. The content stays with the source that owns the ID.

**The bundled catalogue** (details in ARCHITECTURE.md, "The bundled catalogue")

- **The snapshot is the catalogue database itself, gzipped**, not a row dump. Unpacking is one stream to disk (0.45 s) with no rebuild step, and it carries the FTS indexes and the sync state, so the existing incremental sync continues from it unchanged. 13.0 MiB packed against 35.3 MiB unpacked. Compression alternatives measured on the same file: xz 8.0 MB, zstd -19 10.4 MB, gzip -9 13.7 MB. gzip is in `dart:io`, so it adds no dependency and no slow pure-Dart decoder on the phone; xz would save five MB of APK for a few seconds of install. **Provisional:** swap if APK size starts to matter.
- **Committed directly, no Git LFS** (13 MiB is under the 20 MB line, LFS is not installed on bjslab, and a checkout without LFS would silently build an app with no catalogue). It costs about 13 MiB of history per release that changes it. **Flagged:** if releases become frequent, move to LFS or to a release asset fetched in CI.
- **Install rule: no complete catalogue on the device, or the snapshot is newer than the newest per-kind last sync.** A phone that has synced any kind since the snapshot was made keeps its own data (never downgraded; the first version compared against the oldest kind, which could roll back a kind that was newer after an interrupted sync, found in review); a stale one is replaced, and the delta then catches up. The old "Save course / teacher" rows are carried into the new file.
- **The install is staged, checked and swapped, never delete-then-rename.** The staged copy is checked against the manifest (size, `user_version`) before the device's database is touched; failing to read or copy the saved rows abandons the install (a corrupt old file with nothing readable is the exception and is replaced); the old file is renamed to `.previous` and deleted only after the new one is in place, and a crash between the two renames is undone on the next launch. Any failure leaves what was there and falls back to the old first sync.
- **A checkpoint that cannot finish abandons the install.** Before the old file is moved aside its write-ahead log is folded in (`wal_checkpoint(TRUNCATE)`); the pragma reports a blocked checkpoint in its result row rather than throwing, so the result is read and a busy or partial one counts as a failure.
- **No SHA-256 at launch, by decision.** The manifest's hash is checked by a test against the committed asset, and gzip's own CRC covers damage in transit; recomputing the hash in the app cost about 1.1 s on bjslab (about 0.6 s for `quick_check` instead), more on a phone, on every first launch, to guard against a wrong asset that CI already refuses. Size and `user_version` are still checked. Revisit if the snapshot ever comes from anywhere but the build.
- **A first sync killed part-way is still replaced by the snapshot**, even if one kind finished after the snapshot was made (a reviewer suggested keeping the device's data then). The snapshot brings the missing kind (talks, the 124-request bulk of a first sync) whole; the finished kinds are refetched as a delta from the snapshot's editions, a few requests. Only a device with every kind complete is kept.
- **The unpack runs in a worker isolate** (`Isolate.run`), so the ~35 MiB inflate and the SQLite checks do not block the UI thread; the main isolate only awaits, so on the very first launch Home's library still waits for it. Not yet timed on the S23+ (the 0.45 s figure is bjslab); `tools/meditejo/dharma_seed_install_time.dart` measures the unpack itself.
- **The install happens when the database is first opened** (inside the lazy opener), which launch triggers in the background by reading the sync state, and the library's first read triggers anyway. So on the very first launch Home's library waits about half a second on bjslab (longer on a phone) for the unpack. The alternative, installing behind a splash, adds UI for a one-time half second.
- **A failed automatic sync is not retried for 30 minutes** (in memory, so a restart resets it): after four attempts against a failing server, another tab change must not start another round. Pull-to-refresh and the settings row ignore it.
- **The starter set and its `starter_seeded` flag are written in one transaction**, so an interruption leaves either nothing (seeded in full next launch) or everything (never again, so removals stick).
- **Nothing syncs at startup any more.** The delta runs when the user opens Search or Explore (and on a launch that restores Explore), gated by the existing 12-hour rule; pull-to-refresh and the settings row still force it. A consequence: the settings row shows the snapshot's date until Search or Explore is opened.
- **`release.sh` refreshes the snapshot only when the committed one is more than 30 days old**, judged by the `asOf` in `catalogue.json` (it travels with the commit; file times do not), or when `--refresh-catalogue` forces it. Each committed refresh adds about 13 MiB to git history, and the search-time delta sync covers the gap for users, so a release inside the window ships the snapshot already committed. When it does refresh, it is a delta from the committed one (a few requests) and is committed only if Dharma Seed changed something; "nothing changed" means the sync fetched and removed no record, since editions are the server's clock and differ on every call. `--skip-snapshot` never refreshes; combining it with `--refresh-catalogue` is an error. A missing or unreadable manifest counts as stale. Asked for by Burooj's orchestrator.
- **`sqlite3` moved from dev to runtime dependencies**: the installer reads the device database's sync state and carries saved rows across with it before drift opens the file.

On their own, Sounds hold a small `SoundscapeService` (`mediaPlayback`, Stop action, audio focus: pause on loss, resume after a transient loss). It is held through a pause, because starting it again from the background is refused on Android 12 and later. Screen-off playback is unverified on the phone.
- **Fallback, if SoLoud fails on the phone:** move the layers into `AudioPlayerService`, one looping ExoPlayer per layer, plus an `AudioTrack` synth for S2. The `SoundscapeEngine` interface is the seam, so only the engine class changes. Not built.
- **Memory:** each layer is decoded to float (about 23 MB a minute in stereo). Loops are 28–75 s, and a mix holds at most 6 layers.

**Library**

- **22 sounds, all CC0, 8.48 MiB:** 21 from BigSoundBank (Joseph Sardin) and one from OpenGameArt (Ylmir, "Rain (loopable)"). Each licence was read on the sound's own page on 2026-10-19 (`licenseVerifiedOn` in `sources.json`).
  - **Lossless sources over Blanket's lossy edits.** Blanket's CC0 files are Vorbis re-edits of Freesound originals, and its usable CC BY ones would need attribution. BigSoundBank covers every category in FLAC or WAV. No CC BY sound ships, so the credits screen marks none as "attribution required". BigSoundBank's requested courtesy credit appears in every entry anyway.
  - **No accounts.** BigSoundBank's file URLs (the ones its own player uses) download without login; its "free account" only speeds up the download form. Freesound originals need a login, so none were used (see `soundscape-sources.md`).
- **Not auditioned.** Instead of listening:
  - `find_steady.py` picks each loop from the steadiest window of the recording, scored on transient peaks above the median level and on level drift. This avoids cutting a thunderclap, door or voice into a loop.
  - Every loop's seam step sits at an ordinary percentile of its sample steps.
  - Fireplace #3 was dropped: it is sparse pops over near-silence (LRA 26.6 LU), not a bed.
- **Loudness: a static gain, not dynamic loudnorm.**
  - `loudnorm` measures the loop and one gain moves it to −27 LUFS, so the seam keeps one level.
  - Peaky sounds get up to 6 dB of peak limiting under a −2 dBTP ceiling, run over a circularly padded copy so the limiter's state matches across the seam. Beyond that they stay quieter than the target: river −31.8, fire crackle −36.1, wood stove −27.6 LUFS.
- **Encoding:** Ogg Opus at 48 kHz, 64 kbps stereo or 40 kbps mono, with a 4–6 s equal-power crossfade baked into the loop.

**Mixer and UI**

- **One current mix,** as in Blanket. Tapping a sound with nothing playing starts it on its own. Practice plays "the current mix" by default, so a fresh install's first sit gets the first starter preset, *Rain on the forest*, at 50% under the session.
- **Volume:** slider positions are squared into gain. Under a session, the master slider sets that session kind's level and leaves the standalone level alone.
- **Presets:** four starters (*Rain on the forest*, *Night*, *Hearth* with a stove and crackle and no NC fire, and *Shore*), plus the user's own. Long-press deletes one. Built-in names are localised.
- **Practice/Talk defaults** live in the mixer (`SoundscapeSessionDefault`). Talks keep the legacy sound and bells off, as before, and only the soundscape follows its Talks default. The Sounds sheet carries two switches for now; the Customize sheet takes over the full per-kind choice.
- **The Sounds sheet is still `BackgroundSoundView`,** opened by `showBackgroundSoundSheet`, so PR #13's Home quick link and its test need no change. No navigation or Home layout changed.
- **Track titles are English only;** category and preset names are localised in en, de and es.
